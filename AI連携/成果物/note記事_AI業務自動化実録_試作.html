1. 「AIに毎回考えさせる」のではなく「AIが書いたコードに毎回実行させる」

これが全ての土台です。チャットでその都度AIに質問すると、結果がブレるし、コストもかさむし、続かない。 そうではなく——安定して動くPythonコードをAIに書かせ、そのコードを毎日タスクスケジューラで実行させる。 判定の「目」の部分だけClaudeに任せる。これに切り替えてから、初めて「運用」になりました。

2. 最終判断は、必ず人間に残す

AIには一次判定までしかさせていません。

  • 清掃写真 → AIが「対応区分」を提案 → 社員が○×、最後は社長が判断
  • 見積 → AIが過去相場から概算 → 金額の最終確定は人間
  • リフォーム工程 → AIは「仮」のタブにしか書き込まない → 本台帳への昇格は社長の最終判断

「AIの自動書き込みは“仮ステータス止まり”に限定する」。この線引きが、現場が安心して使える理由です。

【有料パート】 購入後に読める本編

1. 使ったツールと、選んだ理由

まず全体像。お金をかけずに始められるものから組みました。

  • Claude(画像認識・コード生成) … 写真判定の「目」と、自動化コードの執筆を担当。
  • Python … AIに書かせた処理を、安定して毎日回すための“実行役”。
  • Windowsのタスクスケジューラ … 「毎晩23時に走らせる」を無人で実現。サーバーやクラウドを別途契約せず、社内のWindows PCを付けたままで運用。
  • 既存のExcel / Googleカレンダー / 物理サーバー … 新しい箱は増やさない。今ある資産の上に乗せるのが、現場が嫌がらないコツでした。

⚠️ 正直な注記:使っているClaudeのモデル世代の表記(Opus / Sonnet / Haiku の各バージョン番号)は、社内ドキュメントの記載をそのまま使っています。最新版かどうかは都度確認してください。AI系は陳腐化が速いので、この記事は随時アップデートします。

2. 定巡(定期巡回)写真の自動判定パイプライン——組み方の実際

これが本丸です。流れはこうです。

① 写真の置き場を決める(真実源) 業者が撮影した写真は、物理サーバー(社内ファイルサーバー)の月フォルダに集約。ここを唯一の入口にします。AIに探させない。決まった場所を機械に走査させる。

② Pythonが当日分(＋遡及3日)を自動で拾う 毎晩23時に起動するスクリプトが、当日撮影ぶん＋過去3日ぶんを走査。撮り直しや遅延アップロードを取りこぼさないよう、遡及3日を入れているのがポイントです。

③ 物件マスターと突合して、プロンプトに“物件情報”を注入する ただ写真を見せるだけでは精度が出ません。担当757棟の物件マスターと突合し、「この物件はこういう物件だ」という文脈をプロンプトに入れてからClaudeに判定させます。同じ写真でも、文脈があると判定が変わる。 たとえば「オーナーが同じ敷地に住んでいる物件」では、庭側を提案に上げないようにする——この“物件特性”はマスターに書いておき、毎回プロンプトに差し込みます。ここが効きました。

④ Claudeが、決まった項目をJSONで返す 判定スクリプト(社内では quality_check.py)がClaudeに投げ、以下をJSON形式で受け取ります(フリーテキストで返させると後工程で使えない。必ず構造化させる)。

  • 清掃品質スコア
  • 撮影品質スコア
  • 草の状態
  • 建物の異常／破損
  • 対応区分(提案／社内是正／別班手配／記録のみ／異常なし)
  • 判定確信度(確実／迷う)

⑤ Excelに蓄積し、“社員が○×を付けるだけ”の日次表を出す 判定結果はExcelの品質履歴に追記。さらに、写真サムネイル＋社員記入欄(★YES / NO / 迷う ＋ ★コメント)付きの日次Excelを、サーバーの月フォルダに自動出力します。出力先は「業者写真と同じ場所」=社員が普段から開くフォルダにしているのがミソで、社員の仕事は「写真を一枚ずつ探して見る」から「並んだサムネに○×を付ける」に変わりました。

真似する時の勘所: - 入口(写真の置き場)を1つに固定する。これだけで自動化の安定度が段違いになります。 - 遡及(さかのぼり)日数を必ず入れる。現場のアップロードは遅れる前提で(うちは3日)。 - 出力は人が5秒で判断できる形(サムネ＋○×欄)に。Excelの生データを渡しても現場は見ません。 - 出力先は現場が普段から開く場所に。専用ツールやローカルPCに置くと、それだけで使われなくなります。

3. Claudeに渡している判定プロンプトの「設計思想」

プロンプト全文は社内固有の物件情報・現場ルールを含むため要点に絞りますが、設計の型はそのまま使えます。

  1. 役割を固定する … 「あなたは建物管理の清掃品質を判定する担当」と立場を与える。
  2. 物件文脈を注入する … マスターから引いた物件情報(種別・状況・オーナー特性など)を本文に差し込む。
  3. 出力をJSONで縛る … 上記6項目を、必ず決まったキーで返させる。自由文を許さない。
  4. 判定哲学を入れる(ここが最重要・次章)。

補足:解像度も「上げれば賢くなる」ではありませんでした。一度1568px→1900pxに上げて細部の白線を拾わせたら、コストが約1.5倍になった上に「記録のみ(=判断保留)」が乱発される副作用が出ました。1568pxに戻し、代わりに「駐車場が主題の写真か?」を先に判定させる型に変えたら、コストを戻したまま必要な検出を維持できました。画質ではなく“見る順番”を設計するほうが効きます。

4. 「過剰検出」をやめさせた——社長のダメ出しを“哲学”に変えたループ

最初の運用で、いちばん効いた改善です。

AIは放っておくと何でもかんでも「要対応」にします。これは現場では困る。社長である私からのダメ出しはこうでした(社内の判定ログに原文で永久記録しています):

「過剰検出は、(お客様に)“金の無心”と取られる」 「提案していいのは3つだけ——①入居者が使う上で困る ②怪我につながる(濡れた苔で滑る等) ③建物本体の重大な劣化」

このダメ出しを、ただ口で言って終わりにしない。仕組みに落とします:

  1. 社員／社長が日次Excelに「NO」と理由を書く
  2. それを取り込むスクリプト(apply_feedback.py)で判定原文をログ化(teijun_feedback_log.xlsx に永久蓄積。二重取り込みを防ぐ processed.json でべき等に)
  3. 現場ルール(§番号付きの FIELD_RULES)を改訂
  4. そのルールを次回のプロンプトに反映
  5. → 次回から判定精度が上がる

これがフィードバックループです。AIに毎回お説教するのではなく、お説教を一度だけして、それをルール化して食わせ続ける。

効いたのは数字でも分かりました。 - 本番初回(57件レビュー)のNO率は約49%。過剰検出が約半数でした。 - 主な誤検出は「駐車場の白線(はっきり見えているのに提案)」「小さな錆を拾いすぎ」「看板を写しただけで提案」「隣家・隣地の誤認」など、パターン化できる失敗ばかり。 - これらを8パターンに整理してルール化(社内ではルールを v6→v7→v8 と版管理)。改訂後の検証では、ある回で人から見た不正解(NO)が2件まで減りました。要確認件数も、旧ルール約19%→改訂版で約8%へ、誤検出が約1/3に低減。

※ ただし直近の正答率の継続的な数字は 【要・実数:社長YES率/NO率の推移】未集計です。盛りません。

勘所:叱る場所を「AI」ではなく「ルールファイル」にする。人間の判断を“原文のまま”残すログ(うちでは「社長判定原則集」)と、AIが食う“圧縮版ルール”を分けておくと、背景を失わずに運用できます。

5. 「高いモデルを使えばいい」ではない——モデル比較の実際

ここは中小企業の運用として、いちばんお伝えしたい所です。

最新の高いモデル(Opus級)をずっと使えば精度は出ます。でも毎晩・年間延べ約14,640回回すと、コストが効いてくる。 そこで、同じ写真群をOpus / Sonnet / Haikuで並行判定させ、判定結果・要確認件数・コストを横並びで出すスクリプト(社内では model_compare.py)を自作しました。

実データ(社内の定巡データ・RKの78枚)での検証結果:

  • Sonnetは「要確認4件」をOpusと完全一致で検出
  • 結論:SonnetはOpus比でコスト約1/4。精度を担保したうえで安いモデルに落とせる

⚠️ 正直な注記その1:これは78枚という限定サンプルでの検証です。「全件で精度同等」を保証するものではありません(社内資料にも同じ注記をしています)。だからこそ、自分の現場のデータで一度比較することを強くおすすめします。比較スクリプトを一本書いておけば、新しいモデルが出るたびに測り直せます。 ⚠️ 正直な注記その2:「1枚◯円」の確定単価は、この記事では出しません。 社内に残っているのは「4月の本番判定で約¥12,000(1回ぶん)」というコスト記録と「Sonnetでおよそ1/4」という相対値だけで、1枚あたりの円単価を私が断言できる根拠がまだありません。盛らないために 【要・実数:1枚あたり/月間のAPIコスト】 として空けておきます。

「とりあえず一番賢いモデル」ではなく、自分のデータで精度を確かめてから一番安いモデルに落とす。これが続けられる運用の分かれ目でした。

6. サウナbotで踏んだ“地雷”——ブラウザ自動操作の暗黙知

家業のサウナでは、4チャネル(CHILLNN・ホットペッパー・トリドリ・電話)の予約とGoogleカレンダーを24時間自動同期するbotが動いています(1チャネルで予約が入ると他チャネルの同枠を自動で売止=クロスロックしてダブルブッキングを防ぐ)。

ここで踏んだ地雷が、他の人の役にも立つはずなので正直に書きます。

  • 「1アカウント1セッション」問題 … 予約サイトの管理画面は、同じアカウントに複数からログインするとセッションを奪い合って壊れる。botが動いている裏で人間が同じ画面を開くと、botが弾かれる。
  • セッションが毎日決まった時間に切れる真因 … ログを調べると、切断時刻が2日連続で「11時台」(11:19 / 11:09)で一致していました。原因は「毎日11時頃に、人間がホットペッパーの管理画面を自分のブラウザで開く」こと。機械のせいではなく、人間の操作とぶつかっていたのです。アイドル維持(keepalive)は生きていたので、原理的にこれでは防げない種類の障害でした。
  • ログイン状態の保持方式 … 「ブラウザのプロファイルごと保持する」方式は脆く、Cookie情報をファイル(state.json)で持つ方式の方が安定だと実証。
  • 無人運用の前提 … 電源接続中はスリープ/休止しない(powercfg のAC設定で確認)／画面ロック中でも「対話型」タスクは動く(ロック≠サインアウト)ことを実機で確認し、Windowsパスワードの設定変更なしで24時間運用にこぎ着けました。
  • おまけの落とし穴 … 自動実行を .bat でラップしたら、cmdが.batをcp932で読むためUTF-8の日本語コメントが文字化けしてエラーになりました。.batのコメントは必ずASCII(英語)で。日本語の説明は別ファイルへ。

教訓:自動化の敵は、たいてい“人間の操作とのバッティング”。技術より先に「いつ・誰が・同じ画面を触るか」を洗い出すと早いです。

8. つまずき集と回避法(正直に全部)

きれいごと抜きで、ハマった所と抜け方を置いておきます。

  • AIが過剰検出する → 「提案していいのは3観点だけ」とルールを明文化し、プロンプトに入れた(第4章)。
  • 判定がブレる → 出力をJSONで縛る。自由文を許すと後工程で使えない。
  • 解像度を上げたら逆に悪化した → 画質ではなく「主題を先に判定させる」型に変える。1568pxで十分(第3章)。
  • ブラウザbotが突然落ちる → 「1アカウント1セッション」を疑う。人間の操作時間とぶつけない(第6章)。
  • ログイン保持が不安定 → プロファイル方式をやめて state.json(Cookie)方式へ。
  • タスクスケジューラが朝に動かない → 実行コマンドにサブコマンドが抜けている／「対話型のみ」でログオフ中は走らない、を疑う。.batでラップし、ログでも成否を確認(撃ちっぱなし起動だと「前回の結果:0」が成功の証拠にならない)。
  • .batが文字化けエラー → コメントはASCIIで。
  • 現場が使ってくれない → 出力を「サムネ＋○×だけ」にし、現場が普段開く場所に置く。生データのExcelは見てもらえない。
  • 写真の取りこぼし → 遡及◯日を必ず入れる(うちは3日)。
  • 「とりあえず最新の賢いモデル」で高コスト → 自分のデータでモデル比較してから安い方に落とす(第5章)。

9. セキュリティ——ここだけは絶対に妥協しない

中小企業ほど、ここで事故ると致命傷です。

  • 認証情報(credentials.json / token.json / state.json / Webhook URL など)は絶対にコミットしない。.gitignore に入れ、ローカル管理を徹底。
  • 秘密性の高いエンドポイント(Webhook URLなど)はリポジトリに置かない。
  • AIエージェントの自動書き込みには合言葉(シークレット)を設定し、無断書き込みを防ぐ。
  • パスワードは人間だけが入力する。AIにはパスワードを打たせない(再ログインが必要なときは人間に誘導するだけ)。

「便利」と「漏らさない」は両立させられます。むしろ最初に線を引いておく方が、後で速いです。

Q&A(よくある不安に先回り)

Q. プログラミングができなくても本当にできる? A. 私はできません。コードはClaudeに書かせ、私は「何を・どの順で・どこまで任せるか」を決めただけです。逆に言うと、現場を一番分かっている人=社長が“何を任せるか”を決めるのがいちばん重要で、そこは外注できません。

Q. AIが間違ったら? A. だからこそ最終判断を人間に残す設計にしています。AIは一次判定／“仮”まで。本確定・本台帳への反映は必ず人が行います。

Q. コストが怖い A. 「一番賢いモデル」を脳死で使うと高くつきます。自分のデータでモデル比較し、精度を担保して安いモデルに落とす——この一手間で大きく変わります(第5章)。

Q. 何から始めればいい? A. いちばん人手が溶けている業務から。かっこいい所からではありません。私の場合は「655物件・年間延べ約14,640回」の巡回写真でした。
